# vaug.in speed pass, 23–24 Nov 2026

Before and after Lighthouse (mobile) for the four pages in the speed plan:
`/`, `/case-studies`, `/case-studies/patient-whatsapp-voice-agent-manchester` and `/book`.

- **Before:** live site on 23 Nov 2026 (21:04 UTC), before any change. One run per page.
- **After:** live site on 24 Nov 2026, after step 4 (commit `b7588b4`). Median of five runs per page.
- **Tool:** Lighthouse 13.6.0 CLI, default mobile settings (simulated slow 4G, 4x CPU slowdown, Moto G Power screen), performance category only, run from a Mac against `https://vaug.in`.
- **Edge caching (step 1) was not active yet:** Cloudflare answered `cf-cache-status: DYNAMIC` for HTML during both measurements, so every request went through to Next.js on Railway.

Targets: LCP under 2.5 s, TBT under 200 ms, CLS under 0.1.

## What changed

| Step | Commit | Change |
| --- | --- | --- |
| 1. HTML edge caching | (Cloudflare, leader) | Not active at measurement time. See the caching notes below. |
| 2. Lighter case-study pages | `7680a08` | Every drawn case-study screen is pre-rendered once in WebKit at 3x (226 WebP images, `frontend/scripts/capture-screens.mjs`, `screens/manifest.ts`). | 3. Smaller JavaScript | `7877a54` | The zoom viewer loads only when someone opens a screen (`next/dynamic`). The drawn fallback scenes, unused since every study has screens or screenshots, no longer ship. |
| 4. Images and fonts | `b7588b4` | Fixed the `/book` layout shift: glow offsets are fixed instead of a % of a band that grows when slots load. ## What's left

1. **TBT under 200 ms on home, `/case-studies` and `/book`.** This means hydrating less:
   - Render the static parts of the big home sections (engagement models, client grid, agent story) on the server, and keep only the interactive bits (filters, hover effects) as small client components.
   - On `/case-studies`, server-render the card grid and leave only the filter bar on the client.
   - Optionally, add `content-visibility: auto` to long below-the-fold sections so the browser skips laying them out until they're near the screen.

   This is a bigger change than steps 2 to 4 and needs its own approval.
2. **TTFB on `/book`.** The extra time isn't server work. The small page arrives in one piece, so its first byte and last byte land together, at about the same total time as the other pages. Larger pages stream, so their first byte comes earlier. Edge caching (step 1) will lower TTFB for every page.
3. **Caching notes for step 1.** Next.js sends `cache-control: s-maxage=31536000` on pre-rendered pages, with `Vary: rsc, next-router-state-tree, next-router-prefetch, …`.
   - If Cloudflare caches HTML, purge it on every deploy (or use a short TTL with stale-while-revalidate).
   - Bypass the cache for requests with `_rsc` in the query or `RSC` / `Next-Router-*` headers.
   - Keep `/api/*` uncached.
4. **Cloudflare email obfuscation** (Scrape Shield) rewrites email links and adds `cdn-cgi/…/email-decode.min.js` to every page, one extra script and a small main-thread task. The address is already in the page's structured data, so it protects little. Turning it off is optional and is a Cloudflare setting, not code.

## How to re-run

```bash
npx lighthouse https://vaug.in/ --only-categories=performance --output=json --output-path=home.json --chrome-flags="--headless=new"
```

Run each page five times and take the median, because TBT varies a lot between runs. Read `server-response-time`, `largest-contentful-paint`, `total-blocking-time`, `cumulative-layout-shift` and `total-byte-weight` from `audits` in the JSON.
